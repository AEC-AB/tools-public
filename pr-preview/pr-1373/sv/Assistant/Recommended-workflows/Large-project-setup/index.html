Recommended setup for large projects

Det här innehållet är inte tillgängligt på ditt språk än.

In a large multidisciplinary project, divide Assistant automation between one central master workflow and Actions files owned by each discipline.

The master workflow manages applications, models, publishing, and the execution context. Each discipline Actions file contains small actions that operate on the current open model. This structure lets a project reuse the same discipline automation in scheduled runs, local design work, and ad-hoc jobs on an automation computer.

Architecture

Section titled “Architecture”

Keep one Master.actions file on a dedicated automation or export computer. The project’s Automation Responsible owns this file.

A typical scheduled run follows this sequence:

The master workflow is responsible for:

  • preparing folders and working areas;
  • downloading or locating project files;
  • looping through project models;
  • starting the required application version;
  • opening each model;
  • selecting and running the correct discipline Actions file;
  • saving, closing, and publishing models;
  • collecting and uploading results;
  • cleaning temporary files;
  • storing run results; and
  • sending success or failure notifications.

Keep model selection, application startup, and publishing in the master workflow. A discipline Actions file receives an open model and performs discipline work on that model.

Use the Loop task, Conditional task, and Run actions file task to build this routing. The Run actions file task passes the current Revit connection to the discipline file. Turn on Run only selected actions when the master workflow must call only part of the discipline file.

Keep the actions small. The master workflow can combine several actions for a nightly run, while an engineer can run only Export IFC during the day.

Scheduled project automation

Section titled “Scheduled project automation”

Use a schedule trigger on the automation computer to start the master workflow outside working hours.

Assistant must remain running with triggers enabled. If Assistant is closed, the trigger cannot start the workflow.

Section titled “Local on-demand actions”

Ad-hoc jobs on the automation computer

Section titled “Ad-hoc jobs on the automation computer”

Use a folder trigger when an engineer needs the automation computer to run a job outside the schedule.

Treat the trigger folder as a submission queue. When Assistant detects an .actions file, it reads the file and deletes the queue copy. Do not create or maintain an Actions file in the trigger folder.

Store each ad-hoc job template in a permanent project location. To submit a job, copy the template into the trigger folder:

The permanent discipline Actions file does not go into the queue. The submitted job only creates the execution context and calls that permanent file.

Define the complete server context

Section titled “Define the complete server context”

A local Shortcut can assume that the correct application and model are already open. An ad-hoc server job cannot make those assumptions.

For Revit, include these steps in the submitted job:

  1. Start the required Revit version.
  2. Open the required model.
  3. Run the permanent discipline Actions file.
  4. Select the required reusable action.

Run history and notifications

Section titled “Run history and notifications”

Enable action-run logging on the automation computer and store .actionrun files in a shared project location. See Log action runs and View runs.

Configure the master workflow to send a final status email after every scheduled run. Send one message after success and another after failure. If neither message arrives, the workflow may not have started.

Discipline workflows can also send a per-model notification. Use these messages when a discipline needs confirmation for each model or needs failures to reach the responsible team directly.

Result Recipient
Master success Automation Responsible
Master failure Automation Responsible
Discipline success Optional discipline recipient
Discipline failure Discipline responsible

The Send mail task requires an Assistant Cloud login. Add Assistant Cloud to the required logins in a shared Actions file.

Workshared Revit models

Section titled “Workshared Revit models”

Classify each action by whether it reads from the model or writes to it. Broad write operations can conflict with active users through element ownership and worksharing.

Actions commonly suited to on-demand daytime use include:

  • exporting IFC;
  • running model checks;
  • creating reports;
  • inspecting model data; and
  • creating coordination output.

Check the behavior of each action before making it available as a Shortcut.

Prefer scheduled execution outside working hours for actions that:

  • write project parameters;
  • update many elements;
  • perform model-wide parameter maintenance;
  • clean up a model; or
  • modify shared model data.

Responsibilities

Section titled “Responsibilities”

Automation Responsible

Section titled “Automation Responsible”

The Automation Responsible maintains:

  • Master.actions;
  • the automation computer and its schedules;
  • common project tasks;
  • application and model startup;
  • save, close, and publish operations;
  • shared .actionrun storage;
  • the ad-hoc trigger folder;
  • stable paths used by automation;
  • final success and failure notifications; and
  • the schedule for write-heavy operations.

Discipline teams

Section titled “Discipline teams”

Each discipline team maintains:

  • its discipline Actions file;
  • small actions that work on the current model;
  • the read or write classification of each action;
  • suitable Shortcuts;
  • approved ad-hoc job templates;
  • discipline-specific notifications; and
  • review of its run results.

Recommended project structure

Section titled “Recommended project structure”

Keep Ad-hoc Templates separate from Ad-hoc Queue. Templates are permanent project files. Queue copies are temporary job requests that Assistant consumes.

Final checklist

Section titled “Final checklist”

Before you enable the project automation, confirm that:

  • the master workflow owns application startup, model selection, saving, closing, and publishing;
  • each discipline action works against the current open model;
  • frequently used safe actions are available through Shortcuts;
  • ad-hoc templates create the full execution context;
  • submitted jobs use stable full paths;
  • the folder trigger is treated as a queue;
  • .actionrun files are stored for later review;
  • the master workflow always reports success or failure; and
  • broad writes to workshared models run when user activity is low.
